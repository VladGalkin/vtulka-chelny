# Организация работы и Git workflow

## Канбан

`Backlog → Planned → In Progress → Review → Done`

## Базовый процесс на одну задачу

1. Выбрать задачу и сформулировать проверяемые критерии приёмки.
2. При необходимости изучить теорию и согласовать проектное решение.
3. Создать отдельную ветку: `docs/VT-012-initialize-repository`, `feat/VT-xxx-...` или `chore/VT-xxx-...`.
4. Внести небольшие логически связанные изменения.
5. Запустить доступные проверки и самостоятельно просмотреть diff.
6. Сделать осмысленный коммит, например `docs: initialize project documentation`.
7. Создать Pull Request, описать результаты, проверки и открытые вопросы.
8. После согласования слить PR в `main`, закрыть связанную Issue и обновить бэклог. В основной локальной папке переключиться на `main` и выполнить `git pull --ff-only`, предварительно сохранив локальные правки.

## Definition of Done для документации

- Документ имеет понятное назначение, дату/статус и ссылки на источники/зависимости.
- Согласованные факты отделены от предположений и открытых вопросов.
- Нет противоречий между Vision, MVP и бэклогом.
- Markdown читается, ссылки на файлы работают.
- Изменения сохранены в Git, не включают секреты.

## Definition of Done для кода — позднее

Функциональность соответствует критериям, проходит необходимые тесты, не содержит секретов, покрывает ошибки и граничные случаи, обновляет документацию и проходит review.

## Принцип работы с Codex

Codex читает `AGENTS.md`; важные решения принимает разработчик. Не предоставлять агенту производственные секреты и не выполнять без проверки опасные операции.
